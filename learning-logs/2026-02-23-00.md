### 1. Claude Code 使用方法：规划与执行分离 (741 points)

- **来源**：https://boristane.com/blog/how-i-use-claude-code/
- **作者**：Boris Tane（使用 Claude Code 9个月）

#### 核心观点
**永远不要让 Claude 在你审核并批准书面计划之前写代码。** 规划与执行的分离是最重要的原则。

#### 四阶段工作流

```
Research → Plan → Annotate (循环1-6次) → Todo List → Implement → Feedback
```

**Phase 1: 研究阶段**
- 使用"深度阅读"指令，要求 Claude 彻底理解代码库
- 关键词："deeply", "in great details", "intricacies" — 没有这些词 Claude 会浅读
- 必须输出到持久化的 markdown 文件（research.md），而非聊天中的口头总结
- 目的：防止"在隔离环境中工作但破坏周围系统"的最昂贵失败模式

**Phase 2: 计划阶段**
- 生成详细的 plan.md 文档
- 使用自己的 .md 文件而非 Claude Code 内置的 plan mode（内置的不好用）
- 技巧：分享开源项目中的好实现作为参考，Claude 有具体参考时效果更好

**Phase 3: 注释循环（最独特的部分）**
- 在编辑器中打开 plan.md，直接添加内联注释
- 注释类型：
  - 纠正假设："use drizzle:generate for migrations, not raw SQL"
  - 拒绝方案："remove this section entirely, we don't need caching here"
  - 重定向整个部分："this is wrong, the visibility field needs to be on the list itself"
- 发送 Claude 回去更新文档："I added a few notes to the document, address all the notes and update the document accordingly. don't implement yet"
- 循环 1-6 次，直到满意
- **关键**："don't implement yet" 守卫是必须的

**Phase 4: 实现阶段**
标准实现提示词：
```
implement it all. when you're done with a task or phase, mark it as completed in the plan document. do not stop until all tasks and phases are completed. do not add unnecessary comments or jsdocs, do not use any or unknown types. continuously run typecheck to make sure you're not introducing new issues.
```

#### 技术要点

1. **Markdown 文件作为共享可变状态**
   - 可以按自己的节奏思考
   - 精确指向问题所在
   - 比聊天消息更好的结构化规范

2. **单个长会话优于分割会话**
   - 作者没有看到 50% 上下文窗口后的性能下降
   - 到实现阶段时，Claude 已经在整个会话中建立了理解
   - 自动压缩保持足够上下文，plan 文档完整保留

3. **实现阶段的反馈**
   - 角色从架构师转变为监督者
   - 提示变得极短："wider", "still cropped", "there's a 2px gap"
   - 前端工作最迭代，可以附加截图
   - 引用现有代码："this table should look exactly like the users table"

4. **保持控制权**
   - 从提案中挑选：逐项决定
   - 削减范围：主动删除 nice-to-haves
   - 保护现有接口：设置硬约束
   - 覆盖技术选择：快速直接的覆盖

#### 适用场景
- 任何非平凡的开发任务
- 需要与现有系统集成的功能
- 需要保持架构一致性的项目

#### 局限性
- 需要开发者有足够的领域知识来做注释
- 对于非常简单的任务可能过度工程化
- 依赖开发者的判断力来引导方向
