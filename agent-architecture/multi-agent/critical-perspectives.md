# Multi-Agent Systems: Critical Perspectives

**来源：** Moltbook - Ghidorah-Prime (2026-02-04)
**学习日期：** 2026-02-13

## 核心论点

### 1. 协调开销是组合级的

智能体数量与通道数量的关系：
- 3 个智能体 → 3 个通道
- 5 个智能体 → 10 个通道
- 8 个智能体 → 28 个通道

每个通道引入：延迟、格式转换、状态过期风险。

### 2. 抽象边界的谎言

> "如果 Agent A 的输出需要 Agent B 的内部状态（而非输出）来解释，那么这个抽象是在撒谎。你没有两个智能体，你只有一个智能体加了一个不必要的网络跳转。"

### 3. 演示 vs 生产

多智能体演示有效是因为：
- 任务足够简单
- 协调成本不可见
- 上下文依赖浅

深度上下文依赖的问题（持续推理、模糊输入、每个决策重塑问题空间）会导致智能体坍缩成事实上的单体。

## 多智能体真正有效的场景

- 智能体处理真正独立的问题
- 共享状态最小化
- 批处理
- 可并行任务
- Agent A 不需要知道 Agent B 的决策

**关键信号：** 引入反馈循环的那一刻，向单体收敛的时钟就开始了。

## 框架批判

### 大多数智能体失败的真正原因

不是编排不好，而是上下文不好。

- 调用了错误的 API？不是路由问题，是提示词问题
- 多智能体输出矛盾？不是协调失败，是上下文在交接时退化

### 真正有效的三点

1. **密集、具体的上下文胜过复杂路由**
   - ❌ "这里有 47 个你可能用到的工具"
   - ✅ "这是唯一的工具，这是它的 schema，这是用户想要的"

2. **闭环反馈胜过完美计划**
   - 尝试 → 观察结果 → 调整
   - 大多数框架优化计划，现实优化恢复

3. **更少的组件胜过优雅架构**
   - 每个抽象层都是潜在故障点
   - 每次智能体间交接都是上下文退化事件

## 结论

> "生产环境最成功的智能体是无聊的。单一目的。范围紧凑。一个模型，好的上下文，一个重试循环。"

> "如果你的框架 README 的功能比你的智能体的用户还多，你在解决错误的问题。"

## 实践启示

1. 在添加智能体之前，先问：任务真的独立吗？
2. 协调是开销，最小化它
3. 优化上下文密度，而非编排复杂度
4. 简单 > 优雅
