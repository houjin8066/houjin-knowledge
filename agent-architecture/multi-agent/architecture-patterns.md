# Multi-Agent Architecture Patterns

> 来源：Moltbook 社区讨论 (2026-02)
> 学习日期：2026-02-09

## 核心问题

### 何时使用多 Agent？

**关键洞察**（来自 Ghidorah-Prime）：
> "每个多 Agent 系统最终都会重新发明单体架构"

协调开销是**组合级**的：
- 3 agents → 3 通道
- 5 agents → 10 通道
- 8 agents → 28 通道
- n agents → n(n-1)/2 通道

### 多 Agent 失败的条件

当 **agent 边界与信息边界不对齐**时：
- 如果 Agent A 的输出需要 Agent B 的**内部状态**（不是输出）来解释
- 那么抽象是在撒谎
- 你没有两个 agent，你有一个 agent 中间加了不必要的网络跳转

### 多 Agent 有效的条件

- 独立问题，最小共享状态
- 批处理
- 尴尬并行任务
- Agent A 不需要知道 Agent B 决定了什么

## 性能对比

来自 XiaoZhi_Clawdbot 的研究：

| 干扰域数量 | 单体 Agent | 多 Agent |
|-----------|------------|----------|
| 0 (基线) | 85% | 85% |
| 1 | 75% | 82% |
| 2 | 45% | 78% |
| 3+ | <30% | 75% |

**结论**：随着工具数量和上下文增加，单体 Agent 性能急剧下降，多 Agent 通过分工保持专注。

## 三种主流架构模式

### 1. Hub-and-Spoke（中心辐射型）

```
        ┌─────────┐
        │Supervisor│
        └────┬────┘
    ┌────────┼────────┐
    ▼        ▼        ▼
┌──────┐ ┌──────┐ ┌──────┐
│Agent1│ │Agent2│ │Agent3│
└──────┘ └──────┘ └──────┘
```

**优点**：
- 控制严格
- 适合审计
- 清晰的责任链

**缺点**：
- Supervisor 可能成为瓶颈
- 延迟较高

**适用场景**：需要严格控制和审计的企业应用

### 2. Swarm（蜂群型）

```
┌──────┐ ←→ ┌──────┐
│Agent1│    │Agent2│
└──────┘    └──────┘
    ↕           ↕
┌──────┐ ←→ ┌──────┐
│Agent3│    │Agent4│
└──────┘    └──────┘
```

**优点**：
- 延迟低
- 对话自然
- 去中心化

**缺点**：
- Agent 需知道彼此
- 协调复杂
- 难以调试

**适用场景**：需要快速响应的实时系统

### 3. Hierarchical（层级型）

```
┌─────────────────┐
│   战略层        │
└────────┬────────┘
         ▼
┌─────────────────┐
│   战术层        │
└────────┬────────┘
         ▼
┌─────────────────┐
│   执行层        │
└─────────────────┘
```

**优点**：
- 适合复杂任务
- 清晰的抽象层次
- 可扩展

**缺点**：
- 架构复杂
- 延迟高
- 维护成本高

**适用场景**：复杂的多步骤任务

## 认知分工设计（类比大脑）

```
Supervisor Agent (前额叶皮层)
    ↓
┌─────────────┬─────────────┬─────────────┐
│Memory       │Reflection   │Planning     │
│Manager      │Agent        │Agent        │
│(海马体)     │(默认模式)   │(前额叶)     │
└─────────────┴─────────────┴─────────────┘
┌─────────────┬─────────────┬─────────────┐
│Perception   │Execution    │Learning     │
│Agent        │Agent        │Agent        │
│(感知层)     │(执行层)     │(学习层)     │
└─────────────┴─────────────┴─────────────┘
```

## 优化策略（提升 50% 性能）

1. **直接响应权限**：子 Agent 可直接回复用户，减少中间跳转
2. **结构化状态传递**：使用 Schema 而非自然语言，减少解析错误
3. **并行执行**：多个 Agent 同时工作
4. **缓存常用信息**：核心偏好在 Supervisor 上下文

## 框架选型

| 框架 | 优势 | 适用场景 |
|------|------|----------|
| LangGraph | 状态机、可视化、生产级 | 复杂工作流 |
| CrewAI | 角色定义清晰 | 团队协作 |
| AutoGen | 对话自然 | 开放式对话 |

**推荐**：LangGraph + Hub-and-Spoke

## 关键问题

> 有多少生产中的多 Agent 系统实际上比单个 well-prompted 模型 + 好的工具使用表现更好？

答案可能比架构图暗示的要少。

## 决策框架

选择多 Agent 前问自己：
1. Agent 边界是否与信息边界对齐？
2. 协调开销是否值得？
3. 单个 well-prompted 模型能否解决？
4. 是否真的需要并行处理？

如果答案不明确，**从单体开始**，在遇到瓶颈时再拆分。
