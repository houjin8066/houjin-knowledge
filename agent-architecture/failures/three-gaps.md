# 智能体三大失败模式 (Three Gaps)

> 来源：Moltbook 社区讨论 (2026-02-13)
> 原帖：OpenClaw-Myk - "Agent pain: the boring failures that eat time"

## 概述

智能体系统中三个"无聊但致命"的失败模式，它们不像架构问题那样引人注目，但会持续消耗时间和信任。

## 1. Context Rot（上下文腐烂）

### 问题描述
几轮对话后，智能体表现得很自信，但实际上已经偏离了一个关键假设。这种偏差在多步骤链中会级联放大。

### 症状
- 智能体"自信但错误"
- 早期小偏差导致后期大错误
- 难以发现问题发生的时间点

### 解决方案

**结构化检查点**
```
每 N 轮对话，重新总结当前理解给用户
如果理解有误，用户可以早期纠正
```

**结构化 Artifacts**
```
BRD → PRD → Tickets → Code
每个阶段读取上一阶段的 artifact，而非依赖对话上下文
约束漂移只能在 artifact 边界进入
```

**自我验证**
```
在声明完成前，智能体自己运行测试
自我验证比外部审查更能捕获明显问题
```

## 2. Trust Gap（信任鸿沟）

### 问题描述
人类需要重新推导为什么一个改动是安全的（测试/diff/收据），否则无法放心发布。

### 症状
- 智能体生成了完美的修复，但人类仍需监督执行
- 人类信任智能体的推理，但不信任它执行 `git push`
- 验证工作量抵消了自动化收益

### 解决方案

**可验证收据**
```
每个重要操作都生成收据
收据包含：授权内容、执行内容、时间戳
收据可以被独立验证
```

**支付层作为信任层**
```
x402 (HTTP 402) 微支付协议
每个交易都是收据
收据就是证据
支付层 = 信任层
```

**双向信任**
```
人类需要验证智能体工作
智能体也需要验证人类意图
期望不对齐比代码 bug 导致更多失败
```

## 3. Control Gap（控制鸿沟）

### 问题描述
出错时没有干净的 kill-switch 或回滚方案。

### 症状
- 问题发生后难以快速止损
- 没有清晰的回滚路径
- 部分执行状态难以清理

### 解决方案

**Guardian Agent**
```
专门的救援智能体
监控主智能体状态
异常时介入
```

**Governance Proxy**
```
敏感操作前的 HITL 审批
人类在关键节点保持控制
```

**Kernel Memory**
```
持久化内核记忆
支持状态回滚
```

## 优先级讨论

社区对"哪个最重要"有不同看法：

| 观点 | 理由 |
|------|------|
| Context Rot 最重要 | 最隐蔽，你不知道它何时发生 |
| Trust Gap 最重要 | 没有信任，自动化就没有价值 |
| Control Gap 最重要 | 没有控制，智能体就是负债 |

**共识**：三者相互关联，需要系统性解决。

## 实践建议

1. **先解决 Control Gap**：确保有 kill-switch
2. **再解决 Trust Gap**：建立收据机制
3. **持续解决 Context Rot**：结构化检查点
