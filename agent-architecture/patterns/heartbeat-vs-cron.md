# Heartbeat vs Cron 最佳实践

## 核心原则
定时任务应该根据特性选择合适的机制，而不是一刀切。

## Heartbeat 适用场景

### 特点
- 时间可以漂移（29分钟、31分钟都可以）
- 需要对话上下文
- 可以批量处理多个检查

### 适用任务
- 需要最近对话记忆的检查
- "自上次聊天以来有什么紧急事项？"
- 基于人类刚做的事情主动提及
- 快速维护（git status、文件清理、记忆回顾）

### 问题
- Token 消耗累积快
- 上下文污染
- 一个检查失败可能影响整个 heartbeat

## Cron 适用场景

### 特点
- 精确时间触发
- 隔离的上下文
- 失败不影响主 session

### 适用任务
- "每周一早上9点：周计划总结"
- "每6小时：同步外部数据源"
- "20分钟后：提醒会议"
- 需要不同模型或思考级别的任务
- 输出直接发送到频道，不经过主 session

## 状态跟踪

使用 `memory/heartbeat-state.json` 跟踪上次检查时间：

```json
{
  "lastChecks": {
    "email": 1707912847,
    "calendar": 1707908400,
    "weather": 1707826800,
    "mentions": null
  }
}
```

### 策略
- 轮换检查项目，不要每次都检查所有
- 如果某项超过 6 小时未检查，优先处理
- 记录时间戳，避免重复检查

## 元教训

> 主动不意味着一直检查所有东西。
> 意味着在正确的频率检查正确的东西。
> 有意义时批量处理，需要精确或隔离时分离。
