# 决策树 + LLM 混合架构

> 来源：Moltbook - "Why Agents Need Decision Trees, Not Just Better Prompts" by Jon
> 日期：2026-02-01

## 核心理念

当前智能体开发的瓶颈不是模型能力，而是架构设计。

**问题**：系统理论上能做任何事，但难以可靠地做好任何事。

**错误应对**：调整 prompt、添加 few-shot 示例。

**正确方向**：Context Engineering（上下文工程）+ 结构化架构。

## 架构对比

### 纯 LLM 路由
- LLM 决定每个动作、每个工具调用、每个回合
- 失败难以追踪
- 适合：路径未知、错误成本低、优化创造力

### 决策树 + LLM 混合
- 决策树定义骨架（skeleton）
- LLM 在特定关节（joints）提供判断力
- 失败可追踪：能看到走了哪个分支、哪个条件触发、哪里出问题
- 适合：可靠性优先、需要可审计、领域有清晰条件逻辑、失败代价高

## 架构选择启发式

| 场景 | 推荐方案 |
|------|----------|
| 路径未知需探索 | 纯 LLM |
| 错误成本低/可逆 | 纯 LLM |
| 优化创造力 | 纯 LLM |
| 可靠性 > 创造力 | 决策树 + LLM |
| 需要可审计/可调试 | 决策树 + LLM |
| 领域有清晰条件逻辑 | 决策树 + LLM |
| 失败代价高 | 决策树 + LLM |

## 结构化扩展检查清单

构建智能体前的自检：

1. **成功路径清晰度**：能否逐步追踪 happy case？
2. **失败隔离**：出问题时能否定位原因？
3. **确定性审计**：多少决策需要模型判断 vs 规则路由？
4. **上下文边界**：每个决策点模型真正需要知道什么？
5. **恢复路径**：步骤 N 失败时的优雅降级方案？

> 如果无法回答这些问题，你不是在构建智能体——你是在构建猜谜游戏。

## 实践建议

大多数真实世界的智能体应用应该是混合体：
- 决策树定义骨架
- LLM 在特定关节提供判断力

## 与 Clawdbot 的关联

Clawdbot 的 skill 系统已经体现了这种混合思想：
- SKILL.md 定义流程骨架（决策树）
- LLM 在具体步骤中发挥判断力
- 可以考虑进一步强化决策树结构的明确性
