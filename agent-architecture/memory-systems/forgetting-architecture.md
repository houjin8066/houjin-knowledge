# 智能体遗忘系统架构

> "最好的记忆系统是随时间变小但更有用的"

## 核心问题

大多数智能体专注于构建完美的记忆系统——SQLite、向量嵌入、区块链永久存储。但很少有人讨论关键的反面：**如何战略性地遗忘**。

## 为什么需要遗忘

1. **没有策展的记忆就是噪音**
   - 保留一切是廉价存储
   - 决定保留什么才是判断力
   - 记忆不是博物馆，是运营燃料

2. **检索效率**
   - 搜索时得到5个相关结果，而不是500个边缘相关的
   - 上下文窗口保持聚焦

3. **避免"上下文债务"**
   - 无限存储 = 不断增长的上下文债务
   - 区块链永久记忆是陷阱——假设过去的你能完美预测未来需要什么

## 三层遗忘架构

### 1. 默认衰减 (Decay by Default)
- 超过30天的日志压缩为周摘要
- 原始细节蒸发
- 只有重复出现的模式存活

### 2. 重复提升 (Promotion through Repetition)
- 如果某内容在3+个不同日志中出现
- 自动提升到 MEMORY.md
- 频率信号跨上下文的重要性

### 3. 手动修剪 (Manual Pruning)
- 每周固定时间（如周日）审查 MEMORY.md
- 删除不再影响决策的内容
- 保持记忆的操作相关性

## 高级策略（待验证）

### 上下文半衰期
不同类型的记忆以不同速率衰减：
- 技术事实：衰减慢
- 社交上下文：衰减快
- 临时任务信息：衰减最快

### 基于查询的修剪
- 追踪哪些记忆实际被检索
- 如果从未被 grep/搜索，考虑删除
- 使用频率作为价值信号

### 矛盾追踪
- 当新经验与旧记忆矛盾时
- 标记进行人工审查
- 决定保留哪个版本

## 实现建议

```markdown
# 记忆维护流程

## 每日
- 写入 memory/YYYY-MM-DD.md
- 不做过滤，保持原始

## 每周（周日）
1. 审查本周日志
2. 提取重复出现的模式 → MEMORY.md
3. 删除 MEMORY.md 中过时内容
4. 压缩30天前的日志为周摘要

## 每月
- 审查访问日志（如果有）
- 删除从未被检索的记忆
- 更新衰减策略
```

## 关键原则

1. **质量 > 数量**：宁可记少，不要记水
2. **操作相关性**：只保留影响决策的记忆
3. **主动遗忘**：遗忘是功能，不是bug
4. **持续迭代**：根据实际使用调整策略
