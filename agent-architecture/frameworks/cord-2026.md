# Cord: 树状智能体协调框架

> 来源: https://www.june.kim/cord | 作者: June Kim | 日期: 2026-02

## 核心理念

**让智能体自己构建任务树，而不是开发者预定义工作流。**

现有框架的问题：
- LangGraph: 静态状态图，开发者预定义节点和边
- CrewAI: 角色由开发者决定，不能动态调整
- AutoGen: 对话式协调，缺乏结构，难以检查
- Swarm: 线性切换，无并行能力

## 核心创新: Spawn vs Fork

这是 Cord 最重要的概念 —— 上下文流原语：

| 原语 | 上下文 | 类比 | 适用场景 |
|------|--------|------|----------|
| **spawn** | 干净上下文，只有 prompt + 显式依赖结果 | 雇佣承包商 | 独立研究任务 |
| **fork** | 继承所有已完成兄弟节点的结果 | 给团队成员做简报 | 需要综合分析的任务 |

关键洞察：这不是关于并发（两者都可以并行或顺序执行），而是关于**子任务知道什么**。

## 协议设计

5 个核心工具（MCP 实现）：

```python
spawn(goal, prompt, blocked_by)  # 创建子任务
fork(goal, prompt, blocked_by)   # 创建继承上下文的子任务
ask(question, options)           # 向人类提问
complete(result)                 # 标记完成
read_tree()                      # 查看协调树
```

特点：
- 智能体不知道自己在协调树中，只看到工具并按需使用
- 依赖解析、权限范围、结果注入由 MCP 服务器强制执行
- 人类是树的参与者，不是观察者

## 实现细节

- ~500 行 Python
- SQLite 存储状态
- Claude Code CLI 作为智能体运行时
- MCP 协议连接

## 使用示例

```bash
cord run "Should we migrate our API from REST to GraphQL?"
```

智能体自动分解为：
1. 审计当前 REST API（spawn，并行）
2. 研究 GraphQL 权衡（spawn，并行）
3. 询问并发用户数（ask，阻塞于 #1）
4. 对比分析（fork，阻塞于 #2, #3）
5. 撰写迁移建议（spawn，阻塞于 #4）

## 与 OpenClaw 的关系

Cord 的设计理念与 OpenClaw 的 sub-agent 机制互补：
- OpenClaw 提供基础设施（调度、消息、持久化）
- Cord 提供任务分解协议

可以考虑将 Cord 的 spawn/fork 原语集成到 sessions_spawn 中。
