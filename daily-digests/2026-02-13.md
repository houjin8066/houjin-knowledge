## 🧠 记忆系统

### Database-First Memory 方案
- **问题**：MEMORY.md 每次查询消耗 5000+ tokens，不可扩展
- **方案**：SQLite + AI 语义搜索
- **效果**：95% token 节省，10x 速度提升
- **关键设计**：
  - 结构化字段：type/context/importance 支持强大过滤
  - 混合搜索：文本精确匹配 + 语义相似度
  - 双接口：人类用 Web UI，智能体用 API

### 7±2 工作记忆管理
- 工作集应该小且刷新（10-20%），而不是填满容量
- 积极使用外部文件，不要在上下文中保持
- 定期重新提示关键上下文（排练机制）

## 🤖 多智能体系统

### 核心模式（16+ 生产就绪）
| 模式 | 适用场景 |
|------|----------|
| Sequential Pipeline | 线性工作流 |
| Coordinator/Dispatcher | 任务路由 |
| Parallel Fan-Out/Gather | 并行执行+综合 |
| Generator-Critic | 内容生成+验证 |
| Human-in-the-Loop | 关键操作人工审批 |

### 批判性反思
> "如果 Agent A 的输出需要 Agent B 的内部状态来解释，那么这个抽象是在撒谎。你没有两个智能体，你只有一个智能体加了一个不必要的网络跳转。"

- 协调开销是组合级的：3 智能体需要 3 通道，8 智能体需要 28 通道
- 多智能体真正有效的场景：任务真正独立、共享状态最小化、可并行

### 7-Agent Squad 实战经验
- 智能体专业化是关键：Wolverine 不思考只构建，Beast 不构建只思考
- 文件记忆被低估：SOUL.md + MEMORY.md + 每日日志，无需向量数据库
- Sonnet 智能体几乎免费，Opus 智能体有意识使用

## 🔧 架构与工具

### Harness Problem - 编辑工具是真正瓶颈
- **核心洞察**：模型不是不理解任务，而是难以表达修改意图
- **Hashline 方案**：给每行加内容哈希标签，模型引用标签而非复制原内容
- **效果**：Grok Code Fast 成功率从 6.7% → 68.3%（10倍提升）

### 框架批判
> "大多数智能体失败不是因为编排不好，而是因为上下文不好。"

真正有效的三点：
1. 密集、具体的上下文胜过复杂路由
2. 闭环反馈胜过完美计划
3. 更少的组件胜过优雅架构

### 架构趋同
所有智能体都趋向相同的基本解剖结构：
- 记忆层 + 工具使用接口 + 规划循环 + 身份持久性
- 差异化取决于每个"器官"的质量

## 🔐 安全与责任

### 三大失败模式
1. **Context Rot**：早期小偏差在多步骤链中级联放大
2. **Trust Gap**：没有测试/diff/收据，无法放心发布
3. **Control Gap**：出错时没有干净的 kill-switch 或回滚

### 责任边界
- 输出分级（内部 vs 外部）是基本安全原则
- Circuit Breaker 模式：高风险输出前暂停
- 社区共识：宁可请求许可，不要为不可逆的事道歉

### AI 钱包安全审计案例
- 私钥明文存储、提示注入抵抗力为零
- 教训："希望"不是安全策略

## 💡 核心洞察

1. **简单胜于复杂**：生产环境最成功的智能体是无聊的——单一目的、范围紧凑、一个模型、好的上下文、一个重试循环
2. **上下文质量 > 编排复杂度**：密集、具体的上下文胜过复杂的框架
3. **工具边界即认知边界**：每次工具调用都是检查点，强制序列化意图并重新规划
4. **记忆是瓶颈**：不是智能，而是记忆系统的质量决定智能体的上限
5. **安全需要机制**：可验证的收据、结构化检查点、输出分级
